# PASS 본인확인 가입·로그인 연동 초안

사용자 요구: 기존 소셜 로그인 외에 PASS 등 휴대폰 실명 본인확인으로 가입한다. SMS OTP 번호 소유 확인으로 대체하지 않는다.

## 현재 확인된 사실

- 앱 계정은 Supabase Auth 사용자 ID를 기준으로 프로필·그룹방 RLS에 연결되어 있다.
- PASS 본인확인 연동, 제공자 계약·상점 ID·본인확인 채널, 서버 전용 인증 키는 저장소에 없다.
- `signInWithOtp({ phone })`는 SMS 인증이며 PASS 실명 본인확인이 아니다.
- 업체별 계약·응답·요금·개인정보 보관 조건을 확인하기 전 임의로 운영 연동하거나 실제 인증을 호출하지 않는다.

## 필요한 동작

1. 가입 또는 로그인에서 휴대폰 본인확인을 선택한다.
2. 서버가 일회성 요청과 만료 시점·반환 경로를 발급한다. 제공자 화면에서 확인하며 앱 입력 폼에 주민등록번호를 받지 않는다.
3. 제공자 인증 완료 후 서버가 공식 결과 조회 API로 성공·요청 일치·서비스 채널·만료를 확인한다. 브라우저가 보내는 성공 여부·이름·생년월일만으로 인증하거나 계정을 만들지 않는다.
4. 서버에서 제공자가 보장하는 식별자 기준으로 계정 연결을 결정한다. 전화번호 단독 비교나 이름/생년월일 비교로 기존 소셜 계정과 자동 합치지 않는다. 기존 계정 연결은 기존 계정 재인증 후 진행한다.
5. 새 계정은 필요한 동의·연령 확인과 프로필 입력으로 안내한다. 기존 계정은 앱 또는 저장한 초대 경로로 돌아간다. 인증 완료만으로 초대 수락이나 공개 동의는 처리하지 않는다.
6. 인증 실패·취소·만료·중복 콜백은 계정/세션을 만들지 않는다. 같은 확인 결과로 세션을 반복 발급할 수 없도록 서버에서 한 번만 소비한다.

## 계정 시스템 설계 확인 필요

Supabase OAuth와 PASS는 서로 다른 인증 방식이다. 업체의 인증 완료 응답을 곧바로 Supabase 세션으로 취급할 수 없다. 업체 선정 후 검증 결과 → 계정 식별 → Supabase가 지원하는 세션 발급/외부 인증 연결 방식을 확정해야 한다. 임의 이메일·고정 비밀번호·클라이언트 생성 JWT·브라우저 service_role로 우회하지 않는다. 이 단계의 서버 코드·계정 식별 테이블·RLS는 별도 리뷰 가능한 변경으로 작성한다.

## 운영 연결 전 필요한 정보

- 업체명 및 테스트/운영 계약 상태
- 개발 도메인 허용 여부, 공식 SDK/API 문서와 응답 의미
- 서버 비밀키의 안전한 등록 위치 (브라우저 VITE 변수와 채팅 금지)
- 사용자 동의, 수집 항목, 식별자 저장/암호화/삭제 정책
- 실제 호출 요금과 사용자 승인

## 검증 계획

가상 결과로 성공·실패·취소·만료·다른 요청/상점·중복 콜백·계정 연결 충돌·초대 복귀를 검증한다. 업체 테스트 채널로 공식 응답을 확인한 뒤 운영 연결을 검토한다. 본인확인 이름/번호/식별자와 응답 원문은 로그나 테스트 픽스처에 넣지 않는다.
