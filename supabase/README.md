# CR-002 DB·RLS 검토 초안

상태: **로컬 검증 완료 / 독립 리뷰·상연님 승인 대기 / 원격 적용 안 함**.
Supabase 조직·프로젝트·Free 플랜은 이 세션에서 확인하지 못했다. claude.ai의 연결은 Codex에 공유되지 않으며 현재 사용 가능한 Supabase 도구·인증 바인딩은 없다. 프로젝트 생성·운영 DB 적용·유료 호출을 실행하지 않았다. 0원 프로젝트 생성 가능 여부도 확인 전이므로 확정하지 않는다.

## 확정 요구사항과 설계 제안

확정: 카카오·구글 로그인, 2명부터 열리는 최대 4명 그룹방, H2는 4명 방만, 만 14세 미만 제외, 동의·차단·신고, 계정 삭제 시 프로필·출생정보·본인이 보낸 메시지 삭제.
아래 테이블·길이 제한·권한 경계는 구현 제안이다. 정책 확정으로 간주하지 않는다.

| 테이블 | 내용 | 일반 로그인 사용자의 접근 |
| --- | --- | --- |
| profiles | 출생일 원본(양/음력·윤달), 검증된 양력일, 시간/모름, MBTI/모름, 연령 확인 시각 | 본인 조회만 |
| display_profiles | 닉네임 | 본인·같은 방 참여자 조회. 차단 관계 제외 |
| consent_records | 서비스·개인정보 동의 문서 버전, 만 14세 확인, 서버 기록 시각 | 본인 조회만. 수정 불가 |
| rooms | 0~4명 현재 인원, 2명 이상 열림 | 구성원 조회만 |
| room_members | 참여자, 별도 궁합 계산 동의 버전·시각, 선택 공개 항목 | 같은 방 조회만 |
| invites | 초대 토큰 SHA-256 해시, 만료·취소 시각 | 직접 접근 불가 |
| messages | 작성자·방·텍스트·전송 시각·당시 인원 | 구성원 조회·본인 명의 전송. 수정 불가 |
| blocks | 차단자·대상 | 본인 목록 조회·같은 방 대상 차단·해제 |
| reports | 신고자·대상·방·메시지 참조·사유 | 본인 신고 조회·같은 방 대상 신고 |

모든 9개 테이블에 RLS 적용. anon은 접근 불가. SECURITY DEFINER는 고정 search_path, 정규화한 테이블명, 제한된 실행 권한을 사용한다. 재귀적인 구성원 RLS 조회는 비공개 cr_private 헬퍼로 처리한다. 이 스키마를 PostgREST 노출 스키마에 추가하면 안 된다.

## 신뢰된 서버가 구현해야 할 경로 (이번 PR에 API 구현 없음)

1. JWT 검증 후 프로필 저장: 사용자 ID를 요청 본문에서 신뢰하지 않는다. 출생일·윤달의 실재 여부를 manseryeok으로 검증하고 양력 변환값을 저장한다. SQL은 기본 범위·양력 일치·한국 날짜 기준 연령을 검사한다. 음력 변환 자체는 SQL에 복제하지 않는다. 동의 버전은 서버가 허용한 버전만 받고 입력값을 로그에 남기지 않는다.
2. 방 생성: 서비스 동의와 별도 계산 동의를 확인한 뒤 방+첫 구성원을 한 트랜잭션으로 생성한다. 시작 인원은 1명(대기), 두 번째부터 열린다. 공개 항목 선택은 계산 동의를 대체하지 않는다.
3. 초대 발급·수락: 서버에서 암호학적으로 무작위 32바이트 이상 토큰 생성, 해시만 저장. 원문 URL·토큰을 로그에 남기지 않는다. 서버에서 해시 대조, 만료·취소, 발급자 현재 소속, 차단 관계, 동의·연령을 확인한다. 초대·방을 정해진 순서로 잠그고 구성원을 추가하는 단일 트랜잭션이 필요하다. SQL은 직접 가입을 막고 동의 기록·최대 인원을 강제하지만 이 초대 수락 API를 대신하지 않는다. 추측 공격 속도 제한도 서버 작업이다.
4. 공개 범위 변경·궁합 계산: 프로필 원본을 다른 참가자의 브라우저에 보내지 않는다. 계산 동의가 있는 현재 구성원만 서버에서 계산한다. 공개 선택된 원본 항목을 돌려줄 서버 응답은 별도 구현·리뷰 대상이다. 궁합 해석에도 원본에서 파생된 정보가 포함됨을 안내한다.
5. 방 나가기·동의 철회: 인증 사용자 본인의 membership만 서버가 삭제한다. 계산 동의 철회 시 방 참여를 제거하는 제안이며 UI 정책은 검토 필요. 구성원 UPDATE는 금지했고, 공개 선택 변경도 서버의 재가입 트랜잭션으로 처리한다(동의 시각을 임의로 새로 만들지 말 것). 향후 변경 전용 RPC 검토 필요.
6. 계정 삭제: 재인증·최종 확인 후 서버가 Supabase Auth 사용자 삭제를 실행한다. 브라우저는 auth.users 삭제 권한이 없다. 서비스 키는 서버 비밀 저장소에만 두며 예시에도 값을 넣지 않는다.

service_role은 Supabase의 의도된 RLS 우회 역할이므로 서버 코드의 권한 확인을 대체할 수 없다. 이 PR은 DB 방어 계층이며 위 경로가 완성되기 전에는 사용자에게 공개하지 않는다.

## 인원·차단·H2

- 구성원 INSERT/DELETE 트리거가 부모 방 카운터를 원자적으로 갱신한다. 4명 제한은 CHECK로 강제하며 동시 가입도 직렬화된다. 카운터·구성원은 일반 사용자 수정 불가.
- 전송 시 같은 방 행을 잠그고 실제 인원을 저장한다. `member_count_at_send=4`인 메시지만 H2 후보로 사용한다. 이것만으로 반복 대화 성공을 선언하지 않는다. 세 명의 초대받은 사람 식별, 집계 기간·반복 횟수 및 성공 기준은 실험 문서와 후속 분석 설계가 필요하다.
- 제안: 양방향 차단 관계의 메시지는 조회에서 제외하고, 차단 상대가 현재 방에 있으면 해당 사용자 간 방 전송을 막는다. 나머지 참여자끼리는 대화할 수 있다. 차단/전송의 완전한 동시 실행 순서 보장은 이번 검증 범위 밖이며 서버 API에서 처리할 필요가 있다. 기존 방 나가기·UI·과거 캐시 정리 정책은 검토 필요.
- 신고 대상과 첨부 메시지는 동일 방/작성자인지 검사한다. 신고 내용은 다른 참가자에게 공개하지 않는다. 운영자 처리 절차·보관 정책은 미정(결정 필요).

## 삭제와 남는 데이터

`auth.users → profiles → display_profiles / consent_records / room_members / invites / messages / blocks / reports`에 CASCADE.
방 생성자 FK만 SET NULL로 하여 생성자 탈퇴가 다른 사람의 메시지를 삭제하지 않는다. 메시지가 삭제되면 신고의 해당 메시지 참조는 SET NULL이다. 신고에 메시지 원문을 자동 복제하지 않는다. 법정 보존 예외는 만들지 않았으며 추가하려면 원문·시행일 확인 필요.

DB에서 행 삭제를 검증했다. 다른 참여자 화면에서도 즉시 사라지려면 후속 앱에서 삭제 통지·재조회·로컬 캐시 무효화를 구현해야 한다. Supabase Realtime publication·실제 삭제 이벤트·웹 푸시 설정은 이번 PR에 포함하지 않는다. 백업 보존·복구 후 삭제 재적용·이미 수신한 화면/외부 복사본 처리는 별도 검토 필요. 계정 삭제가 타인이 직접 입력한 자유문장까지 찾아 지우는 기능은 아니다.

- 초대 만료 기간·취소 권한·반복 사용 정책. DB에 만료값 기본값을 임의로 넣지 않았다.
- 신고 처리 절차·보관 기간, 동의 문서 버전·세부 연령 정책(원문·시행일 확인 필요).
- 차단·공개 범위 변경·동의 철회 UX, H2 상세 집계 기준, 도메인, 간이 성향 테스트 도입 여부.

## 로컬 검증 (실데이터 없음)

격리 Docker의 PostgreSQL 17을 사용한다. 포트 공개·외부 네트워크 없이 auth.users/auth.uid() 대역과 가짜 사용자 6명을 만든다. 실제 Supabase Auth·OAuth·PostgREST·Realtime 통합 검증은 별도 필요.

```sh
docker run --detach --name cr002-review --network none -e POSTGRES_HOST_AUTH_METHOD=trust postgres:17-alpine
docker exec cr002-review pg_isready -U postgres
# 준비 완료 확인 후 실행
docker exec cr002-review createdb -U postgres cr002_test
docker cp supabase cr002-review:/tmp/supabase
docker exec cr002-review psql -X -v ON_ERROR_STOP=1 -U postgres -d cr002_test -f /tmp/supabase/tests/cr002.sql
python3 supabase/tests/concurrency.py
# 이 작업에서 만든 임시 컨테이너만 정리
docker rm -f cr002-review
```

검증: 9개 RLS 활성화, 원본 본인만 조회, 타 방/탈퇴자/비로그인 접근 차단, 작성자·인원 위조 차단, 1명 방 전송 차단, 2/3/4명 상태, 5명 거절, 만 14세 미만 거절, 양방향 차단·신고 비공개, 계정 CASCADE·타인 메시지 보존, 두 세션의 동시 입장 시 한 명만 성공.

운영 적용은 이 검증을 통과했다는 이유만으로 실행하지 않는다. 독립 리뷰, PR #1 수정·merge 후 재검증, 실제 Supabase 환경 검증 계획과 상연님 승인이 먼저다.
